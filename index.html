00

Ground Rules

The one rule that makes everything else legitimate.

00

The rule before you start

Android security testing is only ethical against targets you are authorized to touch. Everything in this manual assumes that boundary is never crossed.

  • Your own Android application.
  • Your own emulator or device.
  • Deliberately vulnerable training applications.
  • A dedicated lab environment.
  • Systems for which you hold explicit, written authorization.
The loop that keeps testing honest
Understand → Identify → Validate safely → Document → Fix → Retest. Exploitation is never the goal; understanding is. A finding you cannot document and remediate is noise.
01

Foundations

What Android is, and the layers it is built from.

01

What is Android?

Android is a mobile operating system built on the Linux kernel and the Android Open Source Project (AOSP). It sits as a software platform between the person using the device and the hardware underneath.

Control flows top to bottom: User → Applications → Android Framework → Runtime and native libraries → HAL → Linux kernel → Hardware.

02

Android Open Source Project (AOSP)

AOSP is the open-source foundation of Android. It contains the framework, system services, runtime, native libraries, system applications, build infrastructure, and kernel integration components.

Manufacturers take AOSP and customize it, which is why two Android phones can behave differently at the security layer.

03

The architecture in detail: the Linux kernel

The Linux kernel is the lowest major software layer. It owns CPU scheduling, memory, processes, filesystems, networking, device drivers, power, security mechanisms, and inter-process communication. Android ships a modified kernel with Android-specific components.

Why the layer order matters for security

Kernel code runs with extremely high privilege, so a kernel vulnerability can have very high impact. A weakness at a lower layer can affect everything above it.

Mental model
The deeper the layer, the more it is trusted and the more damage a bug there can do. Attackers climb; defenders harden each rung.
04

Hardware Abstraction Layer (HAL)

The HAL provides standard interfaces between framework components and hardware-specific implementations — camera, audio, sensors, Bluetooth, biometrics, GPS. Without it, framework developers would have to handle every vendor's hardware directly.

05

The Android Runtime (ART)

Older Android used Dalvik. Modern Android uses ART, the Android Runtime. Apps are written in Java or Kotlin and ultimately execute through the runtime.

  • DEX — the bytecode format the runtime consumes.
  • JIT — just-in-time compilation during execution.
  • AOT — ahead-of-time compilation at install or optimize time.
  • OAT — the optimized, compiled artifact ART produces.
  • Garbage collection — automatic memory management.
02

Application Anatomy

Inside the APK and the four component types.

06

The APK — Android Application Package

An APK is the archive used to distribute and install an app. It bundles resources and executable information into one file.

07

AndroidManifest.xml

The manifest is one of the most important files during a test. It declares package info, the four component types, permissions, intent filters, configuration, and — critically — which components are exported.

First thing to read
Before running anything, read the manifest. Exported components, custom permissions, debuggable and backup flags, and deep-link intent filters all live here.
08

Components: Activity and Service

Activity

An Activity is a UI screen or interaction point — LoginActivity, MainActivity, SettingsActivity. Security-relevant questions: is it exported, how does it handle intents, does it accept deep links, and does it pass sensitive data through intents?

Service

A Service does background work — playback, sync, long-running operations. Concerns: unauthorized invocation, exported services, missing permission enforcement, and sensitive data exposure.

09

Broadcast Receiver

Broadcast receivers respond to broadcast messages, including system events such as boot completion, connectivity changes, and battery state.

  • Unprotected broadcasts that anyone can send or receive.
  • Sensitive information carried inside broadcasts.
  • Improperly exported receivers.
10

Content Provider

Content Providers offer structured data access between applications — contacts, media, app databases, documents.

The core test: can an unauthorized app read or write sensitive data through this provider?

03

System Internals

Binder, system services, and how processes are born.

11

Binder IPC

Binder is Android's primary inter-process communication mechanism. It lets separate processes talk to one another, and most framework services depend on it.

Understanding Binder explains permissions, system services, IPC, app isolation, and privilege boundaries all at once.

12

Android system services

Android exposes many system services — Activity Manager, Package Manager, Window Manager, Power Manager, location, notifications. Apps reach them through framework APIs and IPC.

13

Zygote

Zygote is a fundamental process. New application processes are forked from it, and it preloads parts of the runtime and framework so apps start faster.

Zygote matters for advanced internals and exploit research because every app process inherits from it.

04

The Security Model

Sandbox, permissions, SELinux, Keystore, boot integrity.

14

The application sandbox

A core Android principle: applications are isolated from one another. Historically each app receives its own Linux UID.

This prevents App A from directly reading App B's private files without a proper mechanism or permission.

15

Linux permissions

Android inherits Linux concepts: UID, GID, file ownership, file permissions, and processes.

The purpose is to restrict unauthorized access at the filesystem level.

16

SELinux

SELinux (Security-Enhanced Linux) enforces mandatory access control on top of standard Linux permissions.

DAC vs MAC

  • DAC — Discretionary Access Control, based on owner, group, and file permissions.
  • MAC — Mandatory Access Control, an additional policy layer the owner cannot simply waive.
Why it matters
SELinux is central to Android privilege-escalation study. Even root is constrained by policy in enforcing mode.
17

The permission model

Permissions gate access to protected capabilities: camera, microphone, location, contacts, notifications, Bluetooth, and storage or data depending on the Android version. The model has evolved considerably across releases.

18

Normal vs dangerous permissions

  • Normal — lower-risk permissions that generally do not need a runtime user decision.
  • Dangerous — permissions touching sensitive capabilities or data, requiring stronger authorization.

Modern Android is more granular than this old binary split, but the categories remain a useful lens.

19

Runtime permissions

Modern apps request certain permissions while running rather than only at install.

Testing point: an app must never assume a permission is available without checking.

20

Permission revocation

Users can revoke permissions at any time, so a secure app must not assume a grant is permanent.

21

Android Keystore

The Android Keystore system stores cryptographic keys and can protect them from direct extraction by app code.

  • Key generation and storage inside the system.
  • Hardware-backed security where the device supports it.
  • Authentication-bound keys that require user auth to use.
  • Cryptographic operations performed without exposing the key.
22

Encryption: at rest and in transit

  • Data at rest — protecting information stored on the device.
  • Data in transit — protecting information moving across a network (HTTPS/TLS to the server).
Encryption is not a magic word
Strong cryptography with poor key management is still broken. How keys are generated, stored, and rotated decides whether encryption actually protects anything.
23

Verified Boot

Verified Boot protects the integrity of the OS during startup, detecting unauthorized modification of protected system components.

24

The bootloader

The bootloader starts the operating system. Security-relevant concepts: locked vs unlocked bootloader, Verified Boot, firmware integrity, and the recovery environment.

Unlocking changes the posture
Unlocking a bootloader alters the device's security guarantees and, on many devices, triggers a data wipe.
25

Root access

Root is extremely privileged access. In Linux terms, root = UID 0. A normal app should never hold unrestricted root.

Rooting weakens several security assumptions, though modern Android adds defenses beyond a simple UID check.

26

Root vs exploit

  • Rooting — a process or configuration that provides elevated privileges.
  • Privilege-escalation exploit — a vulnerability that lets a lower-privileged process gain higher privilege.

They are related but not the same. One is a deliberate configuration; the other is an abuse of a flaw.

05

Attack Surface

Every place untrusted input can enter.

27

The Android attack surface

The attack surface spans the whole stack, and each layer can pass input to the next.

External interfaces include network, Bluetooth, NFC, USB, web content, files, intents, deep links, external storage, sensors, and media parsers.

28

The application attack surface

When testing a single APK, walk this surface in order.

06

Analysis & Tooling

Static, dynamic, ADB, the lab, and reverse engineering.

29

Static analysis

Static analysis examines the app without running it: manifest, DEX, resources, strings, URLs, API endpoints, secrets, crypto implementation, permissions, exported components, and native libraries.

Authorized-lab tools: JADX, Apktool, Android Studio, MobSF, and the Android build tools such as aapt.

30

Dynamic analysis

Dynamic analysis observes behavior while the app runs: processes, files, network, IPC, logs, API calls, and how security controls behave in practice.

Common lab tools: ADB, the Android Studio debugger, Frida, Burp Suite, mitmproxy, and logcat.

31

ADB — Android Debug Bridge

ADB is one of the most important tools in Android security. It bridges your computer to a device or emulator.

32

The Android emulator

For learning, an emulator beats attacking someone else's device. You can snapshot and reset the environment after each experiment.

33

A recommended lab

  • Linux
  • Android Studio
  • Android SDK
  • ADB

  • A debuggable test environment

34

APK reverse engineering

A common workflow moves from artifact to understanding to validated finding.

35

DEX

Android apps commonly contain classes.dex. DEX means Dalvik Executable and holds the bytecode the runtime executes. Tools such as JADX decompile it toward readable Java.

36

Smali

Smali is a human-readable representation of Android bytecode instructions — a lower level than decompiled Java, and where you work when logic must be read or patched precisely.

37

Application signing

Android apps are cryptographically signed. Signatures establish app identity, tie updates to the same author, and protect package integrity. Know the signing schemes (v1–v4) and how certificates are handled.

38

Debuggable applications

A debuggable build gains extra debugging capability. That is fine in development but a real risk if it ships to production.

39

Backup security

Backup configuration can pull app data into backups. Ask whether tokens, databases, preferences, credentials, or user data can unintentionally leave the app through backup.

07

Application Vulnerabilities

Storage, IPC, deep links, and WebViews.

40

Insecure data storage

Inappropriate local storage is among the most common mobile problems. Passwords, API keys, session and access tokens, and personal information all get stored insecurely.

Common locations: shared preferences, SQLite databases, files, external storage, logs, and caches.

41

SharedPreferences

SharedPreferences is convenient key-value storage — and convenience is the trap.

Convenience is not a security decision
Sensitive secrets should not sit in plaintext just because SharedPreferences is easy. Use proper cryptographic or Keystore-backed storage.
42

SQLite databases

Apps frequently use SQLite for users, messages, transactions, settings, and cached data. Check for sensitive data, access controls, encryption needs, backup exposure, injection risks, and debug or log leakage.

43

Logging

Apps sometimes log secrets by accident — login tokens, passwords. Production apps must avoid sensitive logging.

44

Intent security

Intents let components communicate. Concerns: untrusted input, exported components, sensitive extras, implicit intents, intent redirection, and URI handling.

45

Exported components

A component may be reachable by other apps depending on its configuration and the Android version.

The question to ask
Does this component truly need to be externally accessible? If not, minimize its exposure.
46

Deep links

Deep links open app functionality from a URL or URI scheme, e.g. myapp://profile/123.

  • Authentication bypass via a link that skips a gate.
  • Unauthorized actions triggered by parameters.
  • Malicious parameters and open redirects.
  • Sensitive information exposed in the link.
47

WebView security

WebView embeds web content inside an app. Issues involve JavaScript, URL validation, unsafe bridges, local file access, untrusted content, mixed content, and navigation handling.

A WebView is not a browser
Do not treat a WebView as equivalent to a hardened browser. It runs inside your app's trust boundary.
48

JavaScript interface risks

Apps can expose Java or Kotlin functionality to JavaScript through a bridge. A poorly designed bridge becomes a serious attack surface.

08

Network & Cryptography

TLS, pinning, auth, tokens, and crypto mistakes.

49

Network security

Apps talk to APIs constantly. The path runs App → HTTPS → API gateway → backend → database.

Examine TLS configuration, certificate validation, authentication, authorization, API tokens, sensitive data in transit, request manipulation, and server-side validation.

50

HTTPS does not mean “secure”

HTTPS protects the channel when implemented correctly. The app can still have broken authentication or authorization, weak tokens, insecure APIs, data exposure, and business-logic flaws.

Remember
HTTPS ≠ complete application security. The transport can be perfect while the logic behind it is wide open.
51

Certificate validation

Apps must correctly validate server certificates: accept valid ones, reject invalid ones, and use appropriate trust configuration. Never disable validation in production to make testing easier — use a controlled lab interception setup instead.

52

Certificate pinning

Pinning compares the server against an expected identity and rejects anything else, making interception harder.

In authorized testing the goal is to judge whether the pinning implementation is correct — not merely to defeat it without understanding it.

53

Authentication

Authentication answers “who are you?” — username and password, OTP, biometrics, passkeys, hardware-backed authentication.

54

Authorization

Authorization answers “what are you allowed to do?” This distinction is critical.

55

Broken access control

An app can look secure on the device while the backend has authorization holes.

If changing the identifier reveals another user's data, the flaw is primarily an authorization problem — and it lives on the server. Test only authorized systems.

56

Token security

Modern apps use session cookies, OAuth tokens, access and refresh tokens, and JWTs. For each, consider storage, expiration, revocation, scope, transmission, leakage, and replay resistance.

57

Cryptography

Symmetric encryption

Same key encrypts and decrypts. Example: AES.

Asymmetric cryptography

Public and private key pairs. Examples: RSA, elliptic-curve cryptography.

Hashing

One-way transformation, e.g. SHA-256. Passwords need password-specific hashing or a KDF (such as bcrypt, scrypt, or Argon2), not a plain hash.

58

Common cryptographic mistakes

  • Hardcoded keys shipped inside the app.
  • Weak or outdated algorithms.
  • Hardcoded IVs or nonces where they must be unique.
  • Reused keys across contexts.
  • Predictable random values.
  • Plaintext secrets.
  • Incorrect certificate validation.
  • Poor key storage.
59

Hardcoded secrets

A secret embedded in an APK should be assumed recoverable, because the APK is distributed to the client.

The rule
Do not treat application binaries as secret storage. Anything shipped to the client is reachable by a determined analyst.
09

The Native Layer

JNI, native libraries, and memory safety.

60

Native libraries

Apps can bundle native code compiled per-ABI.

Native testing touches memory safety, native API misuse, JNI interfaces, hardcoded secrets, and unsafe parsing.

61

JNI

JNI lets Java or Kotlin code call into native C/C++ and back. The boundary itself introduces additional risk, especially memory-safety bugs.

62

Memory-safety vulnerabilities

  • Buffer overflow.
  • Use-after-free.
  • Integer overflow.
  • Out-of-bounds access.
  • Double-free.
  • Improper pointer handling.

Modern Android has many mitigations, but memory safety remains a core topic in native code.

10

Threats & Human Factors

Malware, social engineering, and the network.

63

Malware

Android malware may steal credentials, spy on users, abuse accessibility services, intercept notifications, collect personal data, commit fraud, and maintain persistence.

Contain it
Analyze malware only inside an isolated lab. Never install an unknown APK on your primary, banking, or work phone.
64

Social engineering

Not every attack needs an exploit. Attackers trick users into installing fake apps, granting permissions, entering credentials, opening malicious links, or enabling dangerous settings.

People are attack surface
Human behavior is part of the mobile threat model, not separate from it.
65

Man-in-the-Middle (MITM)

A MITM attack places an attacker between two communicating parties to observe, modify requests, or modify responses.

Correct TLS validation is the key defense. Only intercept systems you are authorized to test.

66

Public Wi-Fi

Untrusted networks add risk. Practical defenses:

  • Use HTTPS everywhere.
  • Avoid unknown networks and verify network names.
  • Keep the OS updated.
  • Never install certificates from untrusted sources.
  • Use trusted VPN or security infrastructure where appropriate.
11

Testing Methodology

A repeatable professional workflow, OWASP, MASVS.

67

A testing methodology

A professional engagement follows a repeatable order from scope to report.

  1. Define scope.
  2. Obtain authorization.
  3. Information gathering.
  4. APK acquisition.
  5. Static analysis.
  6. Manifest analysis.
  7. Dynamic analysis.
  8. Network analysis.
  9. Authentication testing.
  10. Authorization testing.
  11. Data-storage testing.
  12. IPC / component testing.
  13. WebView testing.
  14. Native-code analysis.
  15. Validate findings.
  16. Risk assessment.
  17. Remediation.
  18. Retest.
  19. Report.
68

Reconnaissance

Before testing, gather app name, package name, version, target Android version, permissions, components, APIs, domains, technologies, and native libraries.

Understand before you exploit
Do not start breaking things immediately. First build a clear picture of the application.
69

Threat modeling

  • Assets — what needs protecting? Credentials, money, personal information, tokens, keys.
  • Threat actors — who might attack?
  • Entry points — where can input enter?
  • Trust boundaries — where does trust change?
70

OWASP Mobile Security

The OWASP Mobile Application Security ecosystem is a major learning resource. Key topics:

  • Improper credential usage.
  • Insecure authentication and authorization.
  • Insufficient cryptography.
  • Insecure communication.
  • Insecure data storage.
  • Code quality and code tampering.
  • Reverse engineering and extraneous functionality.

OWASP also provides mobile testing guidance and the MASVS / MASWE resources.

71

MASVS

The OWASP Mobile Application Security Verification Standard sets security requirements for mobile apps across storage, cryptography, authentication, network communication, platform interaction, code quality, and resilience. It is how you move from “learning to hack” to professional testing.

72

Testing categories

Organize your testing into clear buckets so nothing is missed.

  • A — Storage. B — Cryptography. C — Authentication. D — Authorization.
  • E — Network. F — Platform interaction. G — Code quality.
  • H — Reverse engineering. I — Tampering. J — Privacy.
  • K — Native code. L — Backend / API.

A vulnerable-app lab

Deliberately vulnerable apps are the ideal practice target. Split the work three ways and converge on findings.

What to learn first

Do not learn Frida, kernel exploitation, reverse engineering, and malware analysis all at once. Follow the levels.

  1. Level 1 — Linux: files, processes, users, groups, permissions, networking, shell, services.
  2. Level 2 — Android fundamentals: APK, manifest, activities, services, receivers, providers, intents, permissions.
  3. Level 3 — ADB: device connection, shell, package management, logs, files, processes.
  4. Level 4 — Static analysis: JADX, Apktool, DEX, Smali, manifest analysis.
  5. Level 5 — Dynamic analysis: debugging, runtime observation, Frida, logs, files, processes.
  6. Level 6 — Network security: HTTP, HTTPS, TLS, certificates, APIs, authentication, authorization.
  7. Level 7 — Advanced Android: Binder, SELinux, Zygote, ART, native libraries, JNI, kernel.

Hands-On Labs

Eleven guided labs plus malware and incident response.

77

Lab 1 — Understand ADB

Start by identifying the device, then explore the shell and your privilege context.

The point of this first exercise is simply to understand the Android shell and the privilege you run with.

78

Lab 2 — Inspect an APK

Take a deliberately vulnerable APK and determine its package name, version, permissions, activities, services, receivers, providers, libraries, and URLs. Then open it in JADX and Apktool.

Understanding, not exploitation
The goal of this lab is to understand the app — not to immediately break it.
79

Lab 3 — Manifest review

Turn the manifest into a standing checklist you run every time.

  • Package name
  • Version
  • Target SDK
  • Minimum SDK
  • Permissions
  • Exported Activities
  • Exported Services
  • Exported Receivers
  • Content Providers
  • Intent Filters
  • Deep Links
  • Debuggable configuration
  • Backup configuration
80

Lab 4 — Storage review

Look through SharedPreferences, SQLite, files, caches, logs, external storage, and app databases. For each, ask three questions in order.

  1. Is sensitive information stored here?
  2. Who can access it?
  3. Is it encrypted appropriately?
81

Lab 5 — Network review

Map the network architecture, then document what crosses it.

  • Domains and API endpoints.
  • Authentication method and token types.
  • TLS behavior.
  • Sensitive information transmitted.
82

Lab 6 — Authentication review

Test your own vulnerable app against pointed questions.

  • Can authentication be bypassed?
  • Are sessions handled securely?
  • Do tokens expire?
  • Does logout invalidate the session?
  • Are credentials protected?
  • Does the backend enforce authentication?
83

Lab 7 — Authorization review

Create two accounts and prove the boundary between them holds. This is a safe, high-value way to find authorization flaws.

84

Lab 8 — Component security

For every Activity, Service, Receiver, and Provider, run the same interrogation.

  • Is it exported?
  • Why is it exported?
  • Does it require a permission?
  • Does it accept external input?
  • Does it perform a sensitive operation?
85

Lab 9 — WebView security

Using a deliberately vulnerable training app, study URL loading, JavaScript, navigation, JavaScript bridges, local vs external content, and TLS behavior.

The goal is to feel why untrusted web content must never receive unnecessary native privileges.

86

Lab 10 — Reverse engineering

Read the app at two levels. Start high with decompiled Java, then drop lower to smali and resources.

Do this only against intentionally vulnerable applications.

87

Lab 11 — Runtime instrumentation

Later, learn Frida. It lets a researcher observe and instrument application behavior at runtime.

Use it on your own lab apps to understand runtime behavior — not to defeat protections on apps you do not own.

88

Malware analysis lab

For malware research, isolate everything.

Never on production
Never experiment with suspicious APKs on your primary phone, banking device, work phone, or any personal production environment.
89

Incident response

If an Android device is suspected compromised, work in order and preserve evidence.

  1. Disconnect from networks if appropriate.
  2. Preserve evidence.
  3. Avoid destroying logs or data unnecessarily.
  4. Identify suspicious applications.
  5. Review permissions.
  6. Check for unusual account activity.
  7. Review updates and security status.
  8. Change credentials from a trusted device.
  9. Consider professional forensics for serious incidents.
14

Building Secure

Principles and the mistakes beginners make.

90

Secure development principles

When you build apps yourself, hold to these ten.

  1. Minimize permissions.
  2. Don't hardcode secrets.
  3. Use secure cryptographic APIs.
  4. Protect sensitive data.
  5. Validate all external input.
  6. Use HTTPS / TLS correctly.
  7. Enforce authorization server-side.
  8. Don't expose components unnecessarily.
  9. Avoid sensitive logging.
  10. Keep dependencies updated.
91

Common beginner mistakes

  • Thinking Android hacking equals APK modification — it is far broader.
  • Learning only tools — tools are secondary to understanding the OS, architecture, security model, and attack surface.
  • Ignoring backend security — mobile apps are usually clients of a backend that must be tested too.
  • Testing only the UI — real testing covers UI, IPC, storage, network, API, runtime, native code, and OS interaction.
  • Using random malware APKs — dangerous and unnecessary; use controlled vulnerable labs.

93

The one mental model

Don't memorize Android hacking as a list of commands. Think in trust boundaries.

At every boundary, ask the same five questions:

  • Who is allowed to communicate here?
  • What data can cross this boundary?
  • What privilege does the caller have?
  • Is the input trusted?
  • What happens if the caller is malicious?
This is the whole discipline
That mindset is worth more than hundreds of memorized commands. Tools change; trust boundaries don't.

Understand → Identify → Validate safely → Document → Fix → Retest.

Study manual for authorized testing only. Test only systems you own or are explicitly permitted to assess.
